# 分布式训练故障排查

> [!danger]
> 本 Runbook 尚未在统一集群环境中审核。命令、日志入口和恢复动作必须按当前平台确认；不要在证据不足时主动重启、清理或删除任务数据。

## 适用症状

- 任务失败、挂起、无新日志或反复自动重启。
- `POD_FAILED`、节点驱逐/抢占、进程无声退出。
- CUDA error、NCCL timeout、collective mismatch。
- 权重同步、checkpoint、RPC 或 worker actor 失败。

OOM 有独立分流：[[40_Runbooks/OOM 排查|OOM 排查]]。

## 先回答四个问题

1. **任务还活着吗？** 控制面状态、pod 状态、restart/retry 次数是否变化？
2. **最早失败在哪里？** 找首个业务异常或 innermost traceback，不以末端 `connection reset` 代替根因。
3. **影响范围是什么？** 单 rank、单节点、单角色，还是所有 worker 同时失败？
4. **系统卡在哪个 phase？** 初始化、数据、rollout、forward、backward、collective、optimizer、权重同步或 checkpoint？

## 最小证据包

```text
job/task id + trial/retry id
time window + timezone
pod/node/role/PID/rank/local_rank
DP/TP/PP/CP/EP coordinates
last successful phase/step
first failing phase/step
innermost traceback
peer rank symptoms
GPU memory/utilization and host memory
pod lifecycle events and restart count
active config + code commit/image
```

## 分层排查

### 1. 控制面与生命周期

- 任务是 running、failed、evicted、preempted 还是 retrying？
- 新 pod 是否替换旧 pod？日志时间窗是否跨了 retry？
- 调度失败、镜像/挂载/权限问题是否发生在训练代码启动前？

### 2. 角色与拓扑

- 失败进程属于 driver、scheduler、rollout、actor、reference、reward 还是 checkpoint worker？
- 把 global rank 映射为节点、local rank、parallel coordinates 和 GPU。
- 检查 world size 与 group 构造是否和资源分配一致。

### 3. 最早异常

- 从末端错误向前找同一 PID/rank 的第一条 traceback。
- 检查其他 rank 是否更早出现 CUDA/OOM/assert；NCCL timeout 经常是同伴先死后的二次症状。
- 对“无声死亡”补查 pod events、exit code、OOMKilled、节点健康和 host dmesg（若有权限）。

### 4. Collective 与进度一致性

- 所有 group 成员是否进入同一种 collective、相同 tensor count/shape/dtype？
- PP stage 是否处在相同 micro-batch schedule？
- 数据过滤或条件分支是否让部分 rank 跳过 collective？
- timeout 前是否有 rank 在 checkpoint、日志或 CPU I/O 上停留？

### 5. 恢复链

- 自动重试是否复用了旧 rendezvous、端口、共享目录、IPC pool 或 checkpoint 临时文件？
- cleanup 是否真正 stop/join 子线程和子进程、释放共享资源？
- 重复 initialize 是否创建第二套 engine/cache/pool？

## 症状到证据

| 症状 | 首查 | 不要直接下结论 |
| --- | --- | --- |
| NCCL timeout | 最早异常 rank、collective 名称、group、tensor 元数据 | “网络坏了” |
| CUDA illegal access | 第一次 CUDA 异常、异步边界、此前 kernel | traceback 行就是根因行 |
| Connection reset | 对端进程生命周期与更早日志 | RPC 本身有 bug |
| 单 rank 无日志 | pod events、exit code、OOMKilled、node state | Python 死锁 |
| 反复初始化 | PID、retry id、initialize/cleanup 配对 | step 切换必然重建 engine |
| 权重同步失败 | source/target 版本、shard mapping、先前 learner 错误 | upload/download 层是根因 |

## 验证与结束条件

修复后至少验证：

- 相同 phase 能越过原失败点。
- 所有 rank 的 step/collective 重新一致。
- 没有新增 retry、孤儿进程或资源持续增长。
- 指标和 checkpoint 仍到达最终 consumer。
- 记录环境、commit、配置、时间窗和未覆盖风险到 [[50_Experiments/实验索引|实验记录]] 或 incident note。

## 回滚

代码或配置变更前记录原值和生效边界。若 A/B 使失败提前、吞吐显著下降或语义改变，恢复原配置并保留两组证据，不清理原始日志。
