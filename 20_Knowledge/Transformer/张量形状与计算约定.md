# 张量形状与计算约定

## 为什么先写约定

大模型工程中的许多误判来自“同一个符号代表不同范围”：$S$ 可能是全局序列、某个 CP rank 的局部序列、packed token 总数或 decode 当前长度。每次分析先声明坐标系，比直接代公式更重要。

## 推荐符号

| 符号 | 含义 | 常见歧义 |
| --- | --- | --- |
| $B$ | micro-batch 序列数 | 不一定是原始样本数或 rollout 数 |
| $S$ | token 序列长度 | 需标明 global/local、text/vision/raw |
| $H$ | hidden size | 不等于 attention head dim |
| $N_h$ | query head 数 | GQA 中与 KV head 数不同 |
| $N_{kv}$ | KV head 数 | 可能被 TP 切分或复制 |
| $d_h$ | head dim | 通常 $H/N_h$，但先看实现 |
| $V$ | vocabulary size | parallel vocab 可能 padding |
| $L$ | Transformer 层数 | PP stage 只拥有其中一部分 |
| $E$ | expert 数 | 需区分 global 与 local expert |
| $b$ | 每元素字节数 | 参数 dtype、计算 dtype、累积 dtype 可不同 |

## 六类 shape 必须分开

1. **语义 shape**：算法定义中的逻辑形状。
2. **全局 shape**：所有并行 rank 合起来的完整张量。
3. **局部 shape**：当前 rank 实际持有的分片。
4. **存储 shape**：考虑 padding、flatten、packing 后的物理布局。
5. **通信 shape**：collective 或 RPC payload 的形状。
6. **重建 shape**：gather、unpack、反序列化后的 consumer 形状。

只记录 `tensor.shape` 往往只能证明第 3 或第 4 类。

## Dtype 不是单一属性

对一个算子至少区分：

- 输入/参数存储 dtype。
- autocast 后的算子输入 dtype。
- 内部累积 dtype。
- 输出 dtype。
- 通信 dtype。
- loss 或统计量转换后的 dtype。

例如看到 BF16 权重不能推出 logits 最终为 BF16；LM head、logits processor、sampler 或 log-softmax 任一层都可能提升到 FP32。

## 内存单位

若张量含 $n$ 个元素、每个元素 $b$ 字节：

$$
M_{\mathrm{bytes}}=nb,
$$

$$
M_{\mathrm{GiB}}=\frac{nb}{2^{30}}.
$$

必须注明 GB（$10^9$）还是 GiB（$2^{30}$）。视图、别名和共享 storage 不能按逻辑 shape 重复计费；临时 workspace 和 allocator reserve 又可能不体现在存活张量总和中。

## Packing 后的身份

Packed sequence 可能把多条 prompt/response 拼进一个一维 token 流。此时需要额外保留：

- 每段的起止 offset 或 cumulative lengths。
- 样本/请求/session 标识。
- loss mask 与 role mask。
- position IDs 的重置或连续策略。
- 媒体 token 与 media feature 的映射。

否则 shape 相同也无法证明 token 一一对应。
