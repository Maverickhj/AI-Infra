# 跨仓库调用链追踪

## 目标

回答“这个字段最终在哪里消费”“这段逻辑属于哪个仓库”“为什么当前进程改了 tracker 却没有指标”等问题，必须构建可验证的 producer-to-consumer 链，而不是罗列搜索命中。

## 六段式链路

```text
source/config
  -> parser/builder
  -> producer
  -> transport or process boundary
  -> transformation/aggregation
  -> final consumer and side effect
```

每一段记录文件、符号、payload 字段、进程/线程/rank/device 和证据类型。

## 从哪里开始搜

优先聚焦：

1. 模型 class、provider/factory 名称和直接 import。
2. 配置字段的声明、解析和第一次读取。
3. RPC schema、request/response 类型和 batch merge/split。
4. 返回值被 unpack 的 call site。
5. 最终副作用：loss、optimizer、metric sink、文件、网络响应或 collective。

广泛搜索目录名或常见字段通常产生大量低价值命中。先找“创建者”和“最终副作用”，再补中间段。

## 所有权不是文件位置

代码文件位于仓库 A，不代表运行时状态也属于 A：

- 一个 import 可能把仓库 B 的 provider 注入仓库 A 的 runtime。
- Actor method 可能运行在 Ray worker，而 caller 在 driver。
- 同名 module-level singleton 在不同进程中是不同实例。
- event-loop thread 的 CUDA current device 可能不同于创建 backend 的 caller thread。
- `cuda:0` 是进程可见空间的逻辑 ordinal，不一定是物理 GPU0。

## 字段追踪表

| 阶段 | 要记录的内容 |
| --- | --- |
| 声明 | 默认值、类型、合法值 |
| 使能 | enable condition、precedence、环境变量覆盖 |
| 生产 | shape/dtype、样本身份、所在进程/rank |
| 传输 | RPC/IPC/collective、序列化、payload 分类 |
| 转换 | merge/split/filter/cast/shard/gather |
| 消费 | 读取条件、分支、副作用、返回值 |
| 观测 | 日志、metric、dump 由谁发出、最终到哪里 |

## 证明与推断

- 搜到字段定义，只证明它“可以存在”。
- 搜到配置值，只证明静态输入，不证明运行分支生效。
- 搜到 producer，只证明某个对象被创建，不证明跨进程后仍保持身份。
- 搜到 metric 名，只证明有上报代码，不证明到达最终 sink。
- 完整 call chain + runtime 日志可以增强结论，但仍需版本和 topology 上下文。

## 常见过程边界

- CLI/submission process → scheduler/controller。
- Driver → Ray actor/worker。
- HTTP server → tokenizer manager → scheduler/model worker。
- Learner → inference engine weight update。
- Worker local stats → RPC return → DP head merge → logger/TensorBoard。
- CUDA IPC source pool → handle metadata → consumer device reconstruction。

## 输出一个好的链路分析

1. 先给最终结论和真正 owner。
2. 用编号列出 producer 到 consumer 的每一跳。
3. 明确哪些是代码证明、哪些依赖常规启动假设。
4. 标注进程/rank/device 边界。
5. 给一个最小观测方案验证最薄弱的一跳。
6. 如需修改，选择最接近 owner 且 API 影响最小的位置。
