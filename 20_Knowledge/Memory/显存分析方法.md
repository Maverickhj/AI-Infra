# 显存分析方法

## 核心结论

OOM 是某个时刻、某个进程、某张逻辑设备上的**峰值存活集合 + allocator 状态 + 临时申请**超过可用容量。参数量只能解释账本的一部分。

## 显存账本

对训练 rank，可先写：

$$
M_{peak} \approx M_{param}+M_{grad}+M_{optim}+M_{act}+M_{temp}+M_{comm}+M_{runtime}+M_{fragment}.
$$

| 类别 | 例子 | 生命周期 |
| --- | --- | --- |
| 参数 | model weights、master weights | 常驻或按 stage 常驻 |
| 梯度 | grad buffer、main grad | backward 到 optimizer step |
| 优化器 | Adam moments、FP32 master param | 常驻，可能分片/offload |
| 激活 | layer inputs、attention intermediates | forward 到 backward，或重计算 |
| 临时张量 | logits、sort/top-k、loss workspace | 算子/阶段性峰值 |
| 通信 | NCCL buffer、all-gather bucket | collective 周期 |
| Runtime | CUDA context、graph、cache、memory pool | 进程/engine 生命周期 |
| 碎片/预留 | allocator reserved but unused | 随分配历史变化 |

## 静态估算流程

1. 逐项声明 dtype 与 byte width。
2. 声明每一项的 global/per-rank、是否按 DP/TP/PP/CP/EP 分片。
3. 对 activation 写出 $B,S,H,L$ 与 attention 中间量的依赖。
4. 将训练、rollout、reference、reward 等不同进程分开，不因“同一台机器”而合并或忽略。
5. 为 kernel workspace、通信 buffer 和 runtime reserve 留边界，不把理论和运行时峰值混为一谈。

## Activation 的关键变量

- 实际 forward token 数，而非文件名或配置名称中的“128k”。
- packing 后 micro-batch 的 token 总数和最长段。
- checkpoint/recompute 的粒度与覆盖模块。
- PP schedule 同时在飞的 micro-batch 数。
- attention 算法是否物化 $S^2$ 中间量。
- CP/TP/SP 对特定子模块是否真正生效。
- 多模态 raw vision tokens 与注入 LLM 的 vision tokens 是否为同一口径。

## 运行时证据

至少同时收集：

- 失败 phase 与 innermost traceback。
- PID、rank、parallel coordinates、logical CUDA device。
- `allocated`、`reserved`、峰值和 largest free block（若工具可得）。
- micro-batch token/media 规模。
- 失败前后的 allocator snapshot 或分层 profiler。
- 是否发生重试、engine reinitialize、权重同步或 cache/pool 重建。

若 `reserved >> allocated`，碎片化或缓存分配器行为值得调查；若两者都接近容量，更像真实存活集合过大。它们只是分流信号，不是单独的根因证明。

## 优化杠杆的分类

| 杠杆 | 主要减少 | 常见代价 |
| --- | --- | --- |
| 降低 tokens/micro-batch | 激活、临时张量 | 吞吐下降、更多 micro-batch |
| Activation recompute | 激活 | 额外计算 |
| PP/TP/CP | 特定参数或激活 | 通信、bubble、约束 |
| Distributed optimizer | optimizer/grad/param 某些部分 | 通信和实现复杂度 |
| CPU/NVMe offload | GPU 常驻状态 | 带宽与延迟 |
| 缩小 cache/pool | runtime 常驻 | cache 命中和吞吐 |
| 延迟/流式计算 logits | 临时大张量 | 实现复杂度或更多 kernel |

## 从估算到结论

- **静态上界/下界**：由 shape、dtype 和分片规则推导，明确排除项。
- **代码证据**：证明配置能否到达实现、哪个分支生效。
- **运行时观测**：证明某次环境中的峰值和 phase。
- **A/B 实验**：证明某个杠杆是否改变症状。

四者不能互相替代。具体操作见 [[40_Runbooks/OOM 排查|OOM 排查]]。
