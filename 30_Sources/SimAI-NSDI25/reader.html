EN: Introduction · PDF p.2

1 引言：统一仿真的动机

训练性能不是 GPU 理论 FLOPs 的简单函数。训练框架决定事件及 overlap，NCCL 决定 collective 的底层通信模式，真实网络决定传输竞争。把这些环节分开估算，容易错过关键路径。因此，SimAI 选择在统一事件时间线上连接工作负载、计算和通信。

EN: Background and Motivation · PDF p.3–4

2 四个技术目标

高保真 workload、准确的 GPU 计算代价、可还原 NCCL 行为的网络通信、足够快的大规模离散事件模拟。只有同时做到这四项，模拟器才可能用于主机架构选型及反复调参。

EN: SimAI Overview · Figure 1 · PDF p.4

3.1 全局架构

SimAI-WG 负责产生计算与通信事件及依赖，Execution Engine 负责推进事件时间；SimAI-CP 给出计算时间，SimAI-CM 在 SimCCL 产生的 P2P flows 基础上计算通信与网络延迟。应特别区分 SimCCL 的 collective 分解与真正的网络模拟。

EN: Workload Generator · Figure 2 / Tables 1–2 · PDF p.4–6

3.2 工作负载生成

通过单机模拟/截获 Megatron、DeepSpeed 的关键执行路径，生成配置相关的 workload；随后将通信计算之间的阻塞和 overlap 依赖编码。它比固定 trace 更灵活，却要求对 PP rank、优化器、不同并行策略的路径做实际验证。MoE/EP 的 token 分布在论文中采取了平衡假设。

EN: Computation Simulation · Tables 3–4 · PDF p.6–7

3.3 计算时间估计

现有 GPU 优先使用实测子模块 / kernel 时间库，跨设备预估则按计算受限与带宽受限分组做 Roofline 风格外推。后者属于近似模型，不能继承前者的精度指标。需要对照正式 PDF 核对公式分式顺序。

EN: Communication Simulation · Figure 3 / Table 5 · PDF p.7–8

3.4 通信仿真

SimCCL 通过复用 NCCL 初始化、拓扑发现、算法与 channel 选择，输出高层 collective 对应的 P2P 流，再交给通信模拟器。重点是保留 NCCL 的真实通信控制逻辑，同时跳过实际张量收发。PXN 等路径选择会改变 NIC 负载，简单 Ring 公式无法概括。

EN: Large Scale Simulation Speedup · Figure 4 · PDF p.8

3.5 并行仿真加速

网络离散事件引擎经 UNISON 并行，并通过按节点归属拆分状态减少全局锁访问。23× 表示模拟器自身的速度改善，不代表训练性能收益。

EN: Evaluation · Figures 5–9 · PDF p.8–10

4 评估与准确率

论文比较单项 collective、算子计时与端到端 iteration time，并使用 A100/H100 真实集群作为基准。在所选测试中平均相对偏差约为 1.9%，也常被称为 98.1% alignment。它不意味着对每种新模型、MoE 负载或训练框架版本都有同等精度。

EN: In Production Benefits · Figures 10–11 · PDF p.10–11

5 生产应用

通过改变 GPU/网卡带宽组合，比较网络成本带来的边际训练收益；通过改变单机 GPU 数和 TP size，观察计算切分与通信争用的交叉影响。这些结论必须在目标 workload 与集群拓扑上重新验证。

EN: Experience · PDF p.11–12

6 工程演化与服务化

作者经历了粗 workload、手写框架流程、mock 框架、实测 kernel 数据库、NCCL 关键路径模拟、无锁并行优化等阶段。实践上的顺序是先校验工作负载，再校准计算/通信，最后提升模拟速度。服务化需要 GPU 解耦、任务管理与可视化。

EN: Related Work / Conclusion · PDF p.12–13

7–8 总结与适用边界

SimAI 适合训练迭代时间预测、网络/主机协同设计、集体通信对比及参数搜索；不等同于精度/收敛性模拟，也没有证明对任意数据驱动的 MoE routing 或 RL 动态过程保持同等精度。
